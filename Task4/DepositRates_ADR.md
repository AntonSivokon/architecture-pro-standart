# Задание 4. Передача ставок в кол-центр

### **Название задачи:**
Архитектура предоставления актуальных депозитных ставок внутреннему и партнёрскому кол-центрам

### **Автор:**
Команда цифровой трансформации розничного бизнеса

### **Дата:**
2026-11-05

### **Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
| 1 | Менеджер бэк-офиса, АБС, сервис депозитных заявок | Обновление ставок | 1. Менеджер ведёт и подтверждает ставки в АБС. 2. Существующий обработчик синхронизации передаёт ставки сервису. 3. Сервис проверяет и сохраняет их вместе со временем последней успешной синхронизации. |
| 2 | Клиент, оператор банка, CRM кол-центра, сервис депозитных заявок | Консультация клиента по текущим ставкам | 1. Клиент звонит в банк. 2. Оператор открывает ставки в CRM. 3. | 3 | Клиент, сервис депозитных заявок, ответственный сотрудник банка, оператор партнёра, внешняя система партнёра | Консультация клиента в партнёрском кол-центре | 1. Оператор партнёра импортирует файл в свою систему и консультирует клиента. |

Файл содержит дату формирования и срок актуальности; просроченный файл нельзя использовать для консультации. 3. После восстановления синхронизации сервис публикует новую версию. |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| 1 | АБС остаётся источником ставок. CRM и экспорт используют единый проверенный кеш сервиса депозитных заявок; прямой доступ к БД АБС запрещён. |
| 2 | Ставки должны становиться доступны потребителям не позднее 5 минут после успешной синхронизации из АБС. При недоступности источника отображается отметка времени; данные старше 24 часов считаются устаревшими и должны быть явно заблокированы для консультации до подтверждения бизнесом. |
| 3 | REST API доступен только авторизованным системам и ролям банка, работает по защищённому каналу и возвращает только сведения о продуктах и ставках. Доступ и действия экспорта журналируются. |
| 4 | Файл содержит полный актуальный набор ставок, версию, время формирования, дату начала действия, срок актуальности и описание формата. В файле не должно быть персональных данных или данных заявок. |
| 5 | Файл передаётся только через согласованный с партнёром защищённый канал с контролем доступа и фиксацией передачи. Канал не использует API/SFTP; ручной процесс и ответственный сотрудник обязательны. |
| 6 | Система уведомляет ответственных о неуспешной синхронизации и пропущенной выгрузке. Ошибка не должна приводить к выдаче старых ставок без предупреждения. |
| 7 | Новые компоненты используют поддерживаемый банком стек .NET и MS SQL и не требуют изменения технологии CRM подрядчика. |
| 8 | Публикация ставок не должна замедлять приём депозитных заявок; экспорт и интеграция с CRM масштабируются независимо от пользовательского потока. |

### **Решение**

АБС остаётся мастер-системой ставок. Существующий обработчик повторов сервиса депозитных заявок синхронизирует ставки из АБС в хранилище сервиса. Внутренний кол-центр читает их через защищённый read-only REST API: CRM показывает дату и время актуальности, а доступ ограничивается ролью оператора.

В сервис добавляется отдельный обработчик экспорта ставок. Он формирует полный CSV-снимок из того же хранилища, добавляет версию и временные метки, проверяет полноту и публикует результат для контролируемого скачивания через авторизованный интерфейс сервиса. Выгрузка выполняется после изменения ставок и по согласованному регулярному расписанию, как минимум ежедневно. Сотрудник банка передаёт файл оператору партнёра вручную по согласованному защищённому каналу; партнёр импортирует файл через интерфейс своей системы. Прямой машинной интеграции с партнёром нет.

Если источник недоступен, система сохраняет последний успешный снимок, но явно маркирует его устаревшим и не публикует его как актуальную версию. После восстановления синхронизации формируется новый файл. Политика срока годности, расписание, формат CSV и ответственные за ручную передачу фиксируются до запуска.

### **Альтернативы**

1. **Прямое чтение CRM из БД АБС.**
   - Плюсы: не нужен новый интерфейс ставок.
   - Минусы: запрещённый прямой доступ, тесная связанность CRM с Oracle-схемой, дополнительная нагрузка на АБС и риск раскрытия лишних данных.

2. **Единый файл для внутреннего и партнёрского кол-центров.**
   - Плюсы: простая реализация и одинаковый формат данных.
   - Минусы: внутренние операторы не получают актуальность в интерфейсе в реальном времени; ручные выгрузки повышают риск использования устаревших ставок.

3. **Автоматическая интеграция с партнёром по API/SFTP.**
   - Плюсы: быстрее доставка и меньше ручных ошибок.
   - Минусы: не соответствует техническому ограничению партнёра и требует внешнего канала.

4. **Ручная рассылка таблиц по электронной почте.**
   - Плюсы: низкий порог запуска.
   - Минусы: неконтролируемые копии, риск утечки и отсутствие надёжного подтверждения версии и получения; не подходит без специального защищённого процесса.

### **Недостатки, ограничения, риски**

- Ручная передача файла партнёру медленнее API и зависит от сотрудника; нужны назначенный владелец, подтверждение получения и резервный ответственный.
- До запуска необходимо согласовать с партнёром защищённый канал передачи, процедуру импорта и формат файла. Если такой канал не доступен, запуск партнёрского кол-центра блокируется, а не заменяется незащищённой рассылкой.
- Ошибка или задержка синхронизации из АБС одновременно затронет сайт, внутреннюю CRM и экспорт. Нужны мониторинг возраста ставок и оповещения.
- Параллельное использование разных версий файла партнёром может привести к консультации по отменённой ставке. Версия и срок актуальности должны проверяться при импорте и перед использованием.
- Изменения CRM зависят от подрядчика, хотя система развернута в инфраструктуре банка; сроки API-интеграции и тестирования нужно согласовать заранее.
