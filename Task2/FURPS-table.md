# Задание 2. FURPS+ таблица

Требования ниже охватывают MVP цифровой подачи заявок на депозиты и кредиты через сайт и интернет-банк. Пометка **«Дополнительно»** обозначает требование, выведенное из контекста и предлагаемое для уточнения с бизнесом.

| Код | Требования | Комментарий |
|:----|:-----------|:------------|
| F | **Функциональные (Functionality)** | |
| F-01 | На сайте клиент должен видеть доступные депозитные продукты и актуальные ставки, а в интернет-банке - доступные продукты, актуальные и персонализированные ставки. | Архитектурно значимо: ставки сейчас хранятся в XLS-файлах; нужен управляемый источник данных, доступный обоим каналам и бэк-офисам. |
| F-02 | Новый клиент должен иметь возможность подать на сайте заявку на депозит, указав Ф. И. О. и номер телефона. Заявка должна поступить в систему кол-центра для обработки оператором; оператор может предложить особые условия. | Требует интеграции сайта с системой кол-центра подрядчика. Следует сохранять связь заявки и предложенных условий. |
| F-03 | Новый клиент, подавший заявку на депозит через сайт, должен быть направлен в отделение для личной идентификации до открытия депозита. | Обязательное ограничение процесса для нового клиента; заявка с сайта не должна приводить к автоматическому открытию депозита. |
| F-04 | Клиент интернет-банка должен иметь возможность подать заявку на депозит, указав счёт и сумму, и подтвердить отправку СМС-кодом. | Код подтверждения относится к операции подачи заявки; его проверка должна завершиться до регистрации заявки как подтверждённой. |
| F-05 | В MVP менеджер бэк-офиса должен обработать заявку на депозит и подтвердить условия в АБС. Клиенту должны отправляться СМС после подтверждения ставки и после открытия депозита. | Определяет границу MVP: автоматическое открытие без участия бэк-офиса не входит в текущий процесс. |
| F-06 | На сайте клиент должен видеть предложение по кредиту и иметь возможность подать заявку, указав Ф. И. О. и номер телефона. При наличии паспортных данных система должна запросить решение скоринга с использованием доступных данных БКИ. | Условия кредитных продуктов находятся в Кредитном конвейере; для нового клиента нет внутренней истории, поэтому источник данных отличается от процесса для существующего клиента. |
| F-07 | После подачи заявки на кредит через сайт клиент должен получить СМС с указанием обратиться в отделение для получения кредита и идентификации. | Уведомление не должно трактоваться как окончательное одобрение или выдача кредита. |
| F-08 | При обращении в отделение сотрудник должен иметь возможность найти и продолжить заявку на кредит, ранее созданную клиентом на сайте. Для клиента без такой заявки сотрудник создаёт новую заявку. | Нужен единый идентификатор/механизм сопоставления заявок между онлайн-каналом и АБС, исключающий повторное оформление. |
| F-09 | В интернет-банке клиент должен видеть доступные кредиты с актуальными условиями и, если оно имеется, предодобренное предложение с рассчитанной суммой. Клиент должен иметь возможность подать заявку, указав счёт зачисления и необходимые данные, и подтвердить её СМС-кодом. | Предложение и условия должны быть доступны клиентскому каналу из систем, где они формируются и хранятся. |
| F-10 | При подаче заявки по предодобренному предложению система должна повторно оценить клиента упрощённым способом, если его ситуация изменилась. Заявки передаются сотрудникам на обработку. | Повторный скоринг важен для актуальности предложения; при этом дополнительные фоновые предрасчёты скоринга запрещены исходным ограничением. |
| F-11 | Система должна информировать клиента по СМС об изменении статуса кредитной заявки. | Следует определить перечень статусов и события, вызывающие уведомление; не отправлять повторные уведомления при повторной доставке одного события. |
| F-12 | **Дополнительно:** Для заявки необходимо хранить историю статусов, времени изменений и действий сотрудника; клиент и сотрудник должны видеть актуальный статус с учётом этапов обработки. | История нужна для поддержки клиента, разбора спорных ситуаций и надёжной отправки уведомлений. |
| U | **Удобство использования (Usability)** | |
| U-01 | Клиентские интерфейсы сайта и интернет-банка должны соответствовать принятой в банке системе дизайна, включая цвета и брендированные элементы. | Прямое требование бизнеса; обеспечивает согласованный пользовательский опыт в каналах. |
| U-02 | Формы подачи заявки должны понятно объяснять обязательные данные, ошибки заполнения, необходимость СМС-подтверждения и дальнейшие шаги, включая визит в отделение для идентификации нового клиента. | **Дополнительно:** снижает вероятность незавершённых заявок и неверных ожиданий клиента относительно одобрения/открытия продукта. |
| U-03 | **Дополнительно:** Интерфейс должен быть доступным и понятным клиентам с разным уровнем цифровых навыков; на ключевых шагах следует показывать подтверждение успешной отправки и текущий статус заявки. | В банке значительная доля клиентов предпочитает офлайн-обслуживание; доступность онлайн-функций может повлиять на их использование. |
| R | **Надёжность (Reliability)** | |
| R-01 | Сервисы процесса должны быть доступны 24/7 с целевой доступностью 99,9%. Требование распространяется на интернет-банк и задействованные сервисы нового процесса. | Архитектурно значимое целевое требование. Нужно определить границы измерения доступности и исключения для внешних систем. |
| R-02 | Интернет-банк должен сохранять доступность при отказе основного ЦОД, используя резервный ЦОД; решение должно выдерживать требуемую нагрузку после переключения. | Текущее размещение в одном ЦОД и возможность переключения на резервный не подтверждают автоматическое выполнение требования: нужны проверенные процедуры переключения и восстановления. |
| R-03 | **Дополнительно:** Сбой интеграции или внешней системы не должен приводить к потере уже принятой заявки; после восстановления обработка и уведомления должны продолжаться без создания дублей. | В процессе участвуют АБС, кол-центр, СМС-шлюз, Кредитный конвейер и внешнее БКИ; отказ любого из них не должен терять клиентское обращение. |
| R-04 | **Дополнительно:** Повторная доставка заявки, команды подтверждения или события статуса не должна создавать повторную заявку, повторно выполнять связанное бизнес-действие или отправлять дублирующее уведомление. | Необходимое свойство интеграции при сетевых сбоях и повторных попытках; предотвращает расхождения в статусах и повторные действия по заявке. |
| R-05 | Перегруженная АБС не должна получать прямую дополнительную нагрузку от онлайн-каналов в новом процессе; нагрузка на систему кредитного скоринга не должна увеличиваться за счёт фоновых предрасчётов. | Ограничения прямо указаны командами АБС и скоринга. Способ интеграции и допустимые профили нагрузки нужно согласовать с владельцами систем. |
| R-06 | Сервисы интернет-банка и новые компоненты процесса должны допускать горизонтальное масштабирование и распределение запросов между экземплярами и ЦОД. АБС масштабируется вертикально. | Требование к масштабируемости неоднородно для разных систем; архитектура не должна предполагать горизонтальное масштабирование АБС. |
| P | **Производительность (Performance)** | |
| P-01 | Операции должны отвечать максимально быстро; бизнес обозначает целевой отклик в миллисекундах. Справочные данные, которые сейчас загружаются более секунды, должны загружаться быстрее. | Требование пока недостаточно измеримо: нужно согласовать пороги по операциям и перцентили (например, p95/p99), а также разделить время ответа интерфейса и время обработки внешними системами. Нельзя обещать миллисекундный ответ для синхронного скоринга или внешнего вызова без замеров. |
| P-02 | Новый онлайн-процесс не должен ухудшать производительность существующих платежей и других операций АБС/интернет-банка. | **Дополнительно:** необходимы нагрузочное тестирование и мониторинг до запуска, поскольку база АБС уже перегружена, а справочные данные интернет-банка имеют известные задержки. |
| P-03 | **Дополнительно:** Подача заявки должна быстро подтверждаться клиенту, даже если последующая обработка зависит от бэк-офиса или недоступной внешней системы; длительная обработка не должна блокировать интерфейс. | Разделяет быстрый отклик канала и фактическую обработку заявки; особенно актуально для БКИ и суточных интеграций кредитного процесса. |
| P-04 | Предодобренные кредитные заявки ожидаются бизнесом к обработке сотрудниками в течение того же рабочего дня. | Текущее поступление заявок из АБС в Кредитный конвейер выполняется раз в сутки, а ускорить обмен невозможно. Поэтому требование конфликтует с существующим процессом; достижимость срока нужно согласовать и изменить процесс/границы обещания до фиксации SLA. |
| S | **Поддерживаемость (Supportability)** | |
| S-01 | Для новых и изменённых компонентов должна быть подготовлена документация, позволяющая сопровождать решение и расширять его в дальнейшем. | Прямое требование. Документация должна охватывать интерфейсы, потоки данных, эксплуатацию и восстановление. |
| S-02 | По возможности следует использовать технологии, уже применяемые в банке, и технологии, для которых есть внутренняя экспертиза; новые решения должны быть совместимы с существующими платформами разработки. | Сокращает стоимость сопровождения и зависимость от подрядчиков. Внутренние компетенции есть, в частности, по .NET, Oracle/PL-SQL, Java, Python и PostgreSQL. |
| S-03 | **Дополнительно:** Для интеграций и обработки заявок должны быть доступны централизованные журналы, метрики ошибок/задержек и трассировка заявки между системами. | Необходимо для диагностики распределённого процесса и контроля целевых доступности и сроков обработки. Журналы не должны раскрывать лишние персональные данные. |
| S-04 | **Дополнительно:** Изменения должны сопровождаться автоматизированными тестами критичных сценариев и проверкой совместимости интеграций. | Защищает существующие платежи и процессы при развитии интернет-банка и смежных систем. |
| +R | **+ Ограничения (Restrictions)** | |
| +R-01 | Передача чувствительных данных по сайту и интернет-банку должна быть защищена шифрованием трафика. **Дополнительно:** доступ к персональным данным должен предоставляться только уполномоченным сотрудникам; данные в журналах следует минимизировать. | Шифрование передаваемых данных - прямое требование. Контроль доступа и минимизация данных снижают риск раскрытия клиентских данных в банковских системах и логах. |
| +R-02 | Новые технологии должны быть совместимы с действующими платформами и предпочтительно использовать имеющиеся в банке СУБД MS SQL и Oracle и доступную экспертизу. | Не следует выбирать стек, который банк не сможет сопровождать или интегрировать с существующей инфраструктурой. |
| +R-03 | Интернет-банк - монолит на ASP.NET MVC 4.5 / .NET Framework 4.5 с MS SQL, разработанный на платформе подрядчика. Изменения возможны силами банка, но обновление ядра зависит от подрядчика. | Существенное ограничение скорости и свободы изменений. Микросервисный подход допустимо рассматривать в пределах процесса открытия депозитов, но совместимость текущей платформы с Kafka отсутствует. |
| +R-04 | АБС использует десктопный клиент Delphi, Oracle и бизнес-логику на PL/SQL; система разрабатывается внутри банка, база перегружена и допускает только вертикальное масштабирование. | Ограничивает варианты интеграции и масштабирования. Прямой онлайн-доступ каналов к БД или API АБС необходимо исключить либо отдельно обосновать и согласовать. |
| +R-05 | Депозитные ставки сейчас ведутся в XLS-файлах. Решение должно поддержать переход от файлового ведения к управляемой работе сотрудников бэк-офисов депозитов и кредитов с актуальными ставками. | Выбор системы-владельца ставок (например, АБС) требует согласования; в таблице зафиксирована потребность, а не предрешена реализация. |
| +R-06 | Система кол-центра построена на микросервисной платформе подрядчика (React.js, Java Spring Boot, PostgreSQL), поддерживается подрядчиком; SMS-шлюз поддерживается IT банком. | Интеграции зависят от границ ответственности и доступных интерфейсов подрядчиков и телеком-оператора. |
| +R-07 | Кредитный конвейер - Camunda/Oracle с обработчиками на Java; система скоринга - Python/Flask/PostgreSQL с REST API; БКИ - внешняя система с REST API. Обмен заявками и статусами между АБС и конвейером выполняется пакетно раз в сутки и не может быть ускорен в рамках текущего ограничения. | Эти зависимости задают доступные интерфейсы, владельцев изменений и временные ограничения процесса. Суточный обмен несовместим с безусловной гарантией обработки заявки в тот же рабочий день. |
| +R-08 | Функциональность СМС-подтверждения в ядре интернет-банка требует доработки подрядчиком; предпочтительно реализовать необходимую бизнес-логику силами команды банка и не менять ядро без необходимости. | Снижает зависимость от подрядчика, но не отменяет интеграцию с поддерживаемым банком СМС-шлюзом и телеком-оператором. |
| +R-09 | При использовании очередей сообщений предпочтительна Kafka на перспективу, однако текущая платформа интернет-банка с ней несовместима. | Kafka не является безусловным требованием: применение возможно только после решения вопроса совместимости и определения интеграционного компонента. |
